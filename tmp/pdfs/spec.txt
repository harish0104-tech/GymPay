Dashboard Requirements & Development Specification
A practical handoff document for the product designer, frontend developer, backend
developer, QA tester and project owner.
Dashboard Primary purpose
Super Admin Operate the GymPay SaaS platform across all gyms, subscriptions, revenue, support and system
health.
Gym Owner Run one gym: members, memberships, collections, renewals, attendance, staff and reports.
Gym Staff Perform permitted day-to-day counter tasks quickly, with an auditable record of actions.
Gym Customer / Member View membership, pay fees, access receipts, check attendance and manage profile.
Product principle: One GymPay platform serves many separate gyms. A gym must never be able to view or modify
another gym's data. The exact permissions described below should be enforced by the backend, not just hidden in the
interface.

1. Global Product Rules
These rules apply to all four dashboards and should be designed into the application from the start.
1.1 Roles and access
(cid:127) SUPER_ADMIN: GymPay platform operator. Can see cross-gym platform data and manage platform-level settings. Access to
sensitive customer records should be limited to legitimate support needs and logged.
(cid:127) OWNER: Controls one gym's account, members, plans, payments, reports, staff and gym settings.
(cid:127) STAFF: Can perform only the actions granted by the gym owner, such as adding members, recording payments and checking
attendance.
(cid:127) MEMBER: Can access only their own profile, membership, payment history, receipts and attendance.
(cid:127) Every API request must validate the user's role and gym_id/member identity. Hiding a menu item is not security.
1.2 Common interface requirements
(cid:127) Responsive layout for desktop, tablet and mobile; member dashboard should be mobile-first.
(cid:127) Consistent page header, navigation, search, notification area, profile menu and logout.
(cid:127) Every data table should support loading, empty, error and populated states; use pagination for long lists.
(cid:127) Use clear status labels: Active, Trial, Due, Expiring, Expired, Suspended, Paid, Failed, Refunded or Cancelled.
(cid:127) Destructive or financial actions require confirmation and a reason where appropriate.
(cid:127) Display dates in a consistent format and use the gym's configured timezone for dates, renewals and attendance.
(cid:127) Provide accessible labels, keyboard navigation for core actions, readable contrast and clear form validation.
1.3 Key business rules
(cid:127) A payment is a transaction record; do not simply toggle a member's payment status to 'paid'. Keep amount, method, date,
reference, recorder and status.
(cid:127) Membership extension must create or update a membership period with a traceable history. Do not silently overwrite past
periods.
(cid:127) Payment gateway success must be confirmed server-side using a verified webhook/API response; never trust a browser
success message alone.
(cid:127) Automated WhatsApp messages need a log, delivery status, retry handling and duplicate-send prevention.
(cid:127) Do not permanently delete financial transactions. Use void, refund or cancellation states and maintain an audit log.
(cid:127) GymPay's own subscription billing is separate from the gym's collection of membership fees.

6. Shared Workflows and Backend Requirements
These workflows connect the dashboards. The development team should implement them as backend-controlled processes
with auditability.
6.1 Payment-to-membership workflow
Online payment: Member selects Pay Now fi GymPay creates a pending payment/order fi gateway checkout fi
gateway sends webhook fi backend verifies signature and transaction status fi payment becomes successful fi
membership is created/extended according to the gym's renewal rules fi receipt/confirmation is generated fi
dashboards and reports update.
Offline payment: Owner/staff with permission selects member fi enters amount/method/date/reference fi backend records
transaction and recorder fi receipt is generated fi membership period is created/extended if the payment is linked to a
renewal. For UPI/bank transfers recorded manually, clearly distinguish 'staff recorded' from 'gateway verified'.
6.2 Expiry automation workflow
(cid:127) A scheduled backend job runs daily using each gym's configured timezone.
(cid:127) Find memberships due to expire in configured reminder windows; send only if an equivalent reminder has not already been
sent for that membership/window.
(cid:127) Write every attempted message to a WhatsApp/notification log with template, recipient, provider ID, delivery status and error
details.
(cid:127) At expiry, calculate membership status from dates/current membership records; do not rely only on a one-time status update
that can become stale.
(cid:127) Retry transient failures with limits and alert the owner/platform admin after repeated failure.

6.4 Minimum security requirements
(cid:127) Enforce tenant isolation on every server-side query and mutation; gym_id must come from trusted session/authorization
context, not a client-supplied value alone.
(cid:127) Use secure authentication, OTP/session expiry, rate limits and role-based authorization.
(cid:127) Verify payment webhooks, prevent duplicate webhook processing with idempotency keys, and log the gateway
event/reference.
(cid:127) Protect personal information in logs and exports; use least-privilege access and encrypted transport.
(cid:127) Maintain backups and a tested recovery process; restrict production database access.

8. QA / Acceptance Checklist
(cid:127) Role matrix test: try every important action as Super Admin, Owner, Staff and Member; verify both allowed and denied
outcomes.
(cid:127) Tenant isolation test: create two gyms and attempt to access the other gym's members, payments, reports and files by
changing identifiers.
(cid:127) Date boundary test: membership expires today, tomorrow, at month-end, leap day and across timezone boundaries.
(cid:127) Payment test: success, decline, timeout, delayed webhook, duplicate webhook, refund, partial payment if supported and offline
payment correction.
(cid:127) Reminder test: every configured reminder window, opt-out/consent rules, provider outage, duplicate prevention and retry.
(cid:127) Attendance test: active member, expired member, invalid QR, reused QR, double scan and manual override permissions.
(cid:127) Report reconciliation: compare dashboard totals with filtered transaction rows and ensure refunds/voids are treated
consistently.
(cid:127) Mobile test: small screen, poor network, session expiry, form validation, receipt download and QR display.
(cid:127) Audit test: ensure privileged changes and financial corrections record actor, timestamp, reason and old/new values.
(cid:127) Operational test: backup restore, monitoring alerts, support escalation and subscription suspension/reactivation.
